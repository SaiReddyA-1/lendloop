# Architecture decisions

## ADR-001: Repo root is `lendloop/`
The parent directory name contains a space (`Fluence International`), which breaks unquoted shell paths and some tooling. The repo root is the `lendloop/` subfolder; git, npm and CI all run from there.

## ADR-002: `proxy.ts` instead of `middleware.ts`
Next.js 16 renamed request interception to `proxy.ts` (`middleware.ts` is deprecated). Clerk's `clerkMiddleware` is exported from `proxy.ts`. Paths are checked manually (`createRouteMatcher` is deprecated) and `auth.protect()` is called for `/dashboard` and `/admin`.

## ADR-003: Clerk native Convex integration
Convex validates Clerk session tokens directly (`convex/auth.config.ts`, `applicationID: "convex"`, issuer from `CLERK_JWT_ISSUER_DOMAIN`). No custom JWT template: fewer moving parts.

## ADR-004: Route protection in proxy is UX-only
The proxy redirects anonymous users away from `/dashboard` and `/admin`, but the data layer can be reached by other means (direct Convex client calls, stale sessions). The security boundary is Convex: every public function authenticates (`requireUser`/`requireAdmin`) and checks object ownership. Admin = Clerk user id listed in `ADMIN_CLERK_USER_IDS`, verified server-side.

## ADR-005: CSP via Clerk middleware option
`clerkMiddleware({ contentSecurityPolicy })` generates a CSP compatible with Clerk's origins and merges our directives (Convex `connect-src`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`; localhost Convex only outside production). Non-CSP headers (HSTS, nosniff, Referrer-Policy, Permissions-Policy, X-Frame-Options, COOP) are static in `next.config.ts`. Clerk's `strict` mode (nonce + strict-dynamic) is a hardening candidate once pages are verified under it.

## ADR-006: Date handling
Loan dates are calendar dates stored as `YYYY-MM-DD` strings (no time zone), validated by `isIsoDate`. "Today" is computed in UTC (`todayUtc`). Because users live in different time zones, "not in the past" checks allow 1 day of tolerance relative to UTC today.

## ADR-007: Cache Components not enabled
`create-next-app` enabled `cacheComponents`/`partialPrefetching`. They were removed: the app is auth-driven and dynamic, so the feature adds Suspense constraints around Clerk with no caching benefit at this scope.

## ADR-008: Local `cn` helper
The shadcn init emitted imports from a third-party `cn` npm package. Replaced with the standard local `lib/utils.ts` (`clsx` + `tailwind-merge`) to avoid an unnecessary supply-chain dependency.

## ADR-009: NOT_FOUND instead of FORBIDDEN for objects the caller does not own
`requireToolOwner` / `requireLoanParty` throw `NOT_FOUND` both when the object does not exist and when the caller is not allowed to see it. A distinct FORBIDDEN would confirm that an id exists (enumeration / IDOR oracle, API1). FORBIDDEN is reserved for function-level checks (`requireAdmin`, API5) where the function's existence is not secret. Admins only bypass ownership when a call site explicitly passes `allowAdmin: true`.

## ADR-010: Admin bootstrap via `ADMIN_CLERK_USER_IDS` + internal CLI mutations
Admins are identified by Clerk user id (`user_...`, the JWT `sub`), not email: emails can be changed or unverified, ids are immutable and issued by Clerk. `ADMIN_CLERK_USER_IDS` (comma-separated, Convex env, read only in `convex/lib/env.ts`) promotes matching users at `users:ensureCurrent` and writes an audit row (`system:bootstrap`). Day-to-day role changes use `internalMutation`s (`admin:promoteToAdmin`, `admin:demoteToUser`) run via `npx convex run` with the deploy key; they are not callable by clients and audit as `system:cli`.

## ADR-011: The env allowlist never auto-demotes
Removing an id from `ADMIN_CLERK_USER_IDS` does not demote anyone. An env typo or a rollback would otherwise silently strip or (worse, via the inverse) grant privileges. The env is a bootstrap path only; demotion is an explicit, audited CLI action (`admin:demoteToUser`).

## ADR-012: Users are provisioned from verified JWT claims only
`users:ensureCurrent` takes no arguments and builds/refreshes the row solely from `ctx.auth.getUserIdentity()` (tokenIdentifier, subject, name, email). Clients cannot supply role, trusted flag, or ids (API3 BOPLA); Convex's `v.object` validation rejects extra args. Names are sanitized (control chars stripped, capped at 80). `users:me` returns an explicit projection (no tokenIdentifier/clerkUserId).

## ADR-013: Static authorization check (`npm run authz`)
`scripts/check-authz.mjs` fails CI if any public `query`/`mutation`/`action`/`httpAction` export lacks an `// AUTH:` comment directly above it, or (unless it says `public` / `identity-only`) lacks a `requireUser/requireAdmin/requireToolOwner/requireLoanParty` call. It is a regex/paren-matching lint with documented limits (see the script header); it complements, not replaces, behavioural tests and review of `public` claims.

## ADR-014: Approving a request auto-declines overlapping pending requests
When an owner approves a loan, every other *pending* loan on the same tool whose date range overlaps (inclusive) is declined in the same transaction, each with a `request_declined` outbox event to its borrower. Leaving them pending would invite approvals that can only fail the overlap re-check, and would leave borrowers waiting on a request that can never succeed. Approval also re-checks overlap against other approved loans (race safety: Convex mutations are serializable) and rejects expired requests (`endDate` past, with the ADR-006 tolerance).

## ADR-015: Only the owner can mark a loan returned
`loans.markReturned` is owner-only (no borrower, no admin). The lender is the party who can verify the tool is back; letting a borrower self-certify would defeat overdue tracking. Admin intervention, if ever needed, would be an explicit audited internal function.

## ADR-016: Tool removal is a soft delete that cancels pending requests
`tools.remove` sets `status: "removed"` (+ `removedAt`, `removedBy`) instead of deleting, preserving loan history and audit references. It is blocked (CONFLICT) while any approved (unreturned) loan exists, and cancels all pending loans via the state machine actor `system`, emitting `request_cancelled` to each borrower. The logic lives in `convex/lib/toolRemoval.ts` so phase-5 admin removal reuses it (and adds the audit row). Removed tools are NOT_FOUND in `tools.get` even for the owner; owners see them via `tools.listMine` (flagged, `removedByAdmin`).

## ADR-017: Loan date ranges overlap inclusively
Both start and end days are "in use": a loan ending on the 12th conflicts with one starting on the 12th. Dates are whole calendar days, so there is no hand-over time within a day; allowing same-day turnover would need times. `rangesOverlap` in `convex/lib/dates.ts` is the single implementation.

## ADR-018: `take()` caps instead of pagination (for now)
List queries are bounded (tools 200, loans 100 per list, per-tool loan reads 100/200) so no query can scan unbounded data (API4). The MVP board is small enough that a cap is acceptable; production should move to `.paginate()` with cursors and a search index, and surface "showing newest N" in the UI until then. `listIncoming` reads up to 100 per status (`by_owner` sorts by status first), merges by creation time and returns the newest 100 overall.

## ADR-019: Rate limits are indexed counts inside the mutation
`loans.request` enforces max 5 pending requests per borrower (`by_borrower` + status) and max 10 requests per rolling hour (`by_borrower_created`; cancelled requests still count so cancel-spam cannot bypass it); `tools.create` caps 50 active tools per user. Counting inside the mutation is transactional (no race can exceed the cap) and needs no extra dependency, but it only limits business flows, not raw call volume or failed attempts. For production add `@convex-dev/rate-limiter` (token buckets per user/function, including failed calls). Values live in `LIMITS` (`convex/lib/validation.ts`).

## ADR-020: Transactional outbox for loan events
Every loan state change inserts an `automationEvents` row via `enqueueLoanEvent` in the same mutation (ids and type only, no PII). Scheduling of the delivery action is done: `notify.ts` schedules `internal.notifications.deliver` right after the insert. State machine: `convex/lib/loanStateMachine.ts`; derived display status (`active`/`overdue`) is computed at read time, never stored.

## ADR-021: Two secrets, two directions (HMAC out, bearer in)
Convex -> n8n requests are signed with `N8N_WEBHOOK_SECRET` (`X-LendLoop-Signature: sha256=HMAC(secret, "<timestamp>.<rawBody>")` plus `X-LendLoop-Timestamp`; n8n verifies the signature and rejects timestamps older than 300 s, which blocks replay). n8n -> Convex requests present `Authorization: Bearer <N8N_INBOUND_TOKEN>`, compared in constant time (`verifyBearer`). Separate secrets mean a leak in one direction cannot forge the other, and each can be rotated independently. The inbound token is stored in an n8n Header Auth credential, so it never appears in exported workflow JSON. Both are read only in `convex/lib/env.ts`; a missing secret fails closed (outbound: event marked `NOT_CONFIGURED`; inbound: 503).

## ADR-022: Admin removal keeps approved loans; delivery semantics and backoff
Admin `removeTool` cancels PENDING requests (borrowers are notified through the outbox) but does NOT cancel APPROVED loans: the borrower may physically hold the tool and cancelling would erase the record needed to get it returned. The owner-side removal is stricter (blocked while a live approved loan exists). Delivery: an HTTP 2xx from n8n means "delivered"; the workflow must respond only after the email node succeeded (respond-after-last-node), otherwise failures would be hidden. Retryable: 408, 429, 5xx, network error, timeout (10 s originally, 30 s since ADR-028). Backoff after attempt N = [30 s, 2 min, 8 min, 30 min][N-1], max 5 attempts in total (`MAX_ATTEMPTS`/`BACKOFF_MS` in `convex/notifications.ts`; five attempts need only four delays, so the originally planned 2 h entry was dropped). Other 4xx fail immediately (the request is wrong; retrying cannot help). `Idempotency-Key` = event id lets n8n de-duplicate if a 2xx response was lost.

## ADR-023: Server-side idempotency key; no self-trust
Reminder idempotency keys (`<loanId>:<YYYY-MM-DD>`) are computed on the server from validated fields; a client-supplied key is ignored, so n8n retries or a buggy workflow cannot create duplicate reminders or poison the key space. Admins cannot grant or revoke their own `trustedLender` flag (FORBIDDEN): trust is a peer-endorsement signal, so self-assignment is a conflict of interest; another admin must do it. Unchanged values are a no-op and write no audit row.

## ADR-024: Brand palette from onefinops.com, light-only default, AA-adapted primary
Brand colours and fonts (Hanken Grotesk for UI, Instrument Serif for page titles and the wordmark) are adopted from onefinops.com per client request; no logo or name is copied (LendLoop has its own wordmark and loop mark). The site is light-only: the `dark` variant is class-based and no OS `prefers-color-scheme` switching happens. The brand orange `#F1643F` reaches only ~3.2:1 with white text, so `--primary` (buttons, text links) is the darker `#CC4A22` (~4.6:1) with `#B04A22` on hover; `#F1643F` is limited to non-text accents (logo mark, focus ring, active nav bar, selected filter outline). Form-control borders use `--input` `#8A847B` (>= 3:1, WCAG 1.4.11) instead of the decorative `--border` `#ECE8E2`. Muted text is `#69635A` (>= 4.5:1 on white and `#F5F4F0`).

## ADR-025: HMAC secret read from n8n env in a Code node (not the Crypto node)
Workflow 1 verifies signatures in a Code node using `node:crypto` (`createHmac` + `timingSafeEqual`) over the exact raw bytes (webhook option "Raw Body", read with `getBinaryDataBuffer`), with the secret from `$env.LENDLOOP_WEBHOOK_SECRET`. The Crypto node would keep the secret in an encrypted credential, but it cannot compare in constant time and cannot hash `timestamp + raw bytes` without re-serialising the body, so a Code node would still be needed. Trade-offs accepted: the secret is an environment variable of the n8n process (never in workflow JSON, so exports stay clean); `NODE_FUNCTION_ALLOW_BUILTIN=crypto` and `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` must be set (the latter lets any workflow author read all env vars, so n8n editor access must be limited to trusted admins). The inbound bearer token is the opposite case: it lives in an n8n Header Auth credential (encrypted with `N8N_ENCRYPTION_KEY`), created from env by `n8n/scripts/bootstrap.*`, which deletes its temp file.

## ADR-026: n8n-side de-duplication of already-emailed events
n8n keeps the ids of events it has already emailed in workflow static data (newest 500, written by the "Record event" node only AFTER the email node succeeded) and answers repeats with 200 `{"status":"duplicate"}` without sending. Recording after success matters: recording on receipt would turn a Convex retry of a failed delivery into a false "duplicate" and mark the event delivered without an email. Limits: static data persists only for production (published) executions, is per instance, and two concurrent deliveries of one id could both pass (Convex never sends concurrently for one event). Exactly-once email is impossible with SMTP; this gives at-least-once with duplicate suppression for the realistic case (lost 2xx, then retry).

## ADR-027: 502 on email failure so Convex retries
If the Send Email node still fails after its own 3 tries (5 s apart), workflow 1 answers 502 `{"status":"email_failed"}`; Convex treats 5xx as retryable and applies its 30 s / 2 min / 8 min / 30 min backoff. A 4xx would fail the event permanently. Invalid signatures get a bare 401 (no detail, permanent). Unexpected workflow errors (e.g. unsupported `eventType`) surface as HTTP 500, also retried by Convex, and trigger the error workflow (admin email + `workflowErrors` row). n8n's own retry wait is fixed (no exponential option); the real backoff lives in Convex.

## ADR-028: Delivery timeout aligned with n8n retries
n8n's email retries (3 tries x 5 s wait plus SMTP time) can take longer than the original 10 s Convex timeout, which would abort a request n8n then completes (email sent, event retried, only ADR-026 suppresses the repeat). `DELIVERY_TIMEOUT_MS` is now 30 s: longer than n8n's worst case for one event, short enough to bound an action.

## ADR-029: n8n and Mailpit are not publicly exposed
`docker-compose.yml` binds n8n (5678) and the Mailpit UI (8025) to `127.0.0.1`; Mailpit SMTP (1025) is reachable only on the compose network. Convex must reach the webhook, so production needs a reverse proxy exposing ONLY `/webhook/lendloop-loan-events` over HTTPS (editor and REST API stay private, `N8N_SECURE_COOKIE` back to true). The webhook is authenticated by HMAC, not by network position. Image tags are pinned (n8n 2.46.6, Mailpit v1.33.0); the only mounts are the named data volumes plus read-only `workflows/` and `scripts/`.

## ADR-030: Authorization lint is a tokenizer-based allowlist, with a self-test
`scripts/check-authz.mjs` now blanks comments and string/template/regex literals before matching, so a guard (or an export) that only appears in a comment or string no longer counts. It follows aliases (`import { query as q }`, `import * as s`, `queryGeneric`), `export const X: Type = builder(`, wrapped builders, `export default` and `export { x as y }`, rejects `export ... from` re-exports, and scans `convex/lib/**`, `*.test.ts` and `test.setup.ts` where ANY public builder is a failure (helpers must not become client-callable). `// AUTH: public` / `identity-only` is accepted only for the `PUBLIC_ALLOWLIST` in the script (`tools.ts#listPublic`, `users.ts#me`, `users.ts#ensureCurrent`, `http.ts#methodNotAllowed`), so a new public endpoint is a reviewed change to the lint itself. `npm run authz:selftest` runs fixtures in `scripts/__fixtures__/authz` (every bad case must fail with the expected message, the good case must pass) and is part of `npm run check`. Still a lint, not a proof: it does not prove a guard runs first or on every path.

## ADR-031: n8n encryption key as a Docker secret file
`N8N_ENCRYPTION_KEY` is no longer in `n8n/.env` / the container environment. Compose mounts `n8n/secrets/n8n_encryption_key` as a secret and sets `N8N_ENCRYPTION_KEY_FILE=/run/secrets/n8n_encryption_key` (n8n reads `<NAME>_FILE` for every config env var; verified in `@n8n/config` of 2.46). Because `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` (ADR-025) exposes the whole environment to workflow authors, keeping the key out of the environment means an editor can read `LENDLOOP_WEBHOOK_SECRET` (accepted, needed by the Code node) but not the key that protects stored credentials. `N8N_SECURE_COOKIE` / `N8N_PROTOCOL` stay local-only defaults (`false` / `http`) but are overridable (`${VAR:-default}`); the compose file flags them as local-only. Upgrade note: an existing install must put its CURRENT key in the secret file (n8n refuses a different key).

## ADR-032: Public display names never come from the email
`users:ensureCurrent` builds the public name from `name`, then `givenName` (plus the initial of `familyName`), then "Neighbor". The email local-part is never used (it is shown to other users on listings and loans and is often a real name or handle); a name claim that itself contains `@` is ignored. Existing rows are corrected the next time that user signs in.

## ADR-033: Abuse limits on requests and tool creation
Beyond the pending cap (5) and hourly cap (10), a borrower may create at most `MAX_REQUESTS_PER_TOOL_PER_DAY = 2` requests per tool in a rolling 24h, counting every status including cancelled (index `by_borrower_tool_created`), so request/cancel cycling cannot flood an owner with emails. Tool creation is limited to `MAX_TOOL_CREATES_PER_HOUR = 10` per owner (index `by_owner_created`, removed tools count). `tools:listMine` reads active and removed tools separately (active first, then at most 50 removed) so removed rows cannot hide active ones. Both limits answer `RATE_LIMITED`.

## ADR-034: Zero-width and bidi characters are stripped from user text
`sanitizeText` removes `U+200B-200F`, `U+202A-202E`, `U+2060-2069` and `U+FEFF` (invisible, enable spoofing such as right-to-left override in names and tool titles) in addition to control characters. The n8n compose Code nodes apply the same stripping before escaping, as defence in depth for rows written before this change.

## ADR-035: Bounded overdue scan and reminder date window
`GET /api/n8n/overdue-loans` walks the `by_status_endDate` range (approved, endDate before today) oldest-first in pages of 100 (one paginated query per call, so the HTTP action loops), skips loans already reminded today, and stops after 100 loans or 1000 scanned rows. Already-reminded loans therefore never starve newer ones. Known limit: with more than about 1000 overdue approved loans the tail is not reached in one run. `recordReminder` accepts only `reminderDate` within +-1 day of today (UTC) and answers 400 `invalid_body` otherwise, so n8n (or a leaked token) cannot write arbitrary-date reminder rows.

## ADR-036: Short secrets and plain-http webhooks fail closed
`N8N_INBOUND_TOKEN` and `N8N_WEBHOOK_SECRET` shorter than 32 characters are treated as not configured (inbound: 503 `not_configured`; outbound: event fails `NOT_CONFIGURED`). `N8N_WEBHOOK_URL` must be `https:` unless the host is `localhost`, `127.0.0.1`, `host.docker.internal` or `[::1]`; credentials in the URL are refused; otherwise the event fails with `INSECURE_WEBHOOK_URL` (the payload carries recipient name and email). Both checks live in `convex/lib/env.ts`.

## ADR-037: Outbox sweeper, admin re-drive, batched bulk operations
A 10-minute cron (`convex/crons.ts` -> `maintenance.sweepStuckEvents`) re-schedules delivery for `pending` events not updated for 10 minutes and without a future `nextAttemptAt` (100 per run; `deliver` still caps total attempts). HTTP 401 from n8n stays a permanent failure (a bad signature or a clock skew beyond the n8n tolerance will not fix itself by retrying; keep Convex and n8n clocks on NTP). Admins can re-drive a `failed` event (`admin.retryAutomationEvent`: resets attempts, back to `pending`, schedules delivery, audit action `automation.retry`; `workflow_error` and `overdue_reminder` rows are not retryable) from a "Failed notifications" section above the workflow errors, with a confirm dialog and toast. Tool removal and the approve auto-decline process at most `BULK_BATCH_SIZE = 1000` loans per transaction (about 3 writes each, far below the 8192-write limit) and schedule `maintenance.continueToolRemoval` / `continueAutoDecline` for any remainder, replacing the old fixed `take(500)` / `take(200)` that silently left pending requests behind.

## ADR-038: Secret scan rules and no silent skips
`scripts/scan-secrets.mjs` also flags `whsec_` values, JWTs, Convex deploy keys, `*SECRET|TOKEN|KEY|PASSWORD = <24+ opaque chars>` in non-example files, and 64-hex strings in non-JSON source (lock files and the RFC vectors in `convex/lib/hmac.test.ts` are allowlisted). Placeholders (`replace-with-...`, `your-...`) are fine; an explicit `scan-secrets:allow` marker on a line is the escape hatch for test values. Unreadable files are reported and fail the scan (exit 2), oversize/deleted files are listed as notes, and a git failure fails the scan instead of passing on an empty list. `npm run scan:secrets:selftest` builds secret-shaped fixtures at run time (so the repo holds none) and is part of `npm run check`.

## ADR-039: Workflow 2 continues past a single failed reminder record; HSTS without preload
In the overdue-reminders workflow the "Record reminder" HTTP node uses `onError: continueRegularOutput` (after its 3 tries), so one 4xx (409 loan returned mid-run, 404) cannot abort the remaining reminders; the "Get overdue loans" step still fails the run and fires the error workflow. Trade-off: if Convex is down while recording, that loan may be reminded again on a same-day re-run. `next.config.ts` drops `preload` from HSTS (keeps `max-age=63072000; includeSubDomains`): preload is effectively irreversible and covers every subdomain, so it is a per-domain opt-in once the production domain is final.

## ADR-040: Tool photos in Convex file storage, validated on attach
One optional photo per tool (`tools.photoId`, `v.id("_storage")`). Flow: `toolPhotos.generateUploadUrl` (requireUser, 20 per rolling hour per user, ledger table `uploadIntents`, `RATE_LIMITED`) -> client POSTs the file -> `toolPhotos.attachPhoto` (requireToolOwner, tool must be active). Attach reads `ctx.db.system.get("_storage", id)` and accepts only `image/jpeg|png|webp` up to `LIMITS.PHOTO_MAX_BYTES` (2 MB), then reads the first bytes and requires the magic numbers to match the declared type (`convex/lib/imageSniff.ts`), because the stored Content-Type is client supplied (OWASP File Upload Cheat Sheet; SVG is excluded since it can carry script). A file already referenced by any tool (`by_photoId`) is never re-attached or deleted, so a leaked id cannot be used to steal or destroy another listing's photo. Replacing or removing a photo, and removing a tool (owner or admin, `lib/toolRemoval.ts`), deletes the stored file. Deviation from "throw VALIDATION": a Convex mutation that throws rolls back all its writes, including `storage.delete`, so a rejected upload would survive. `attachPhoto` therefore deletes the file and returns `{ ok: false, message }` for content problems (wrong type, size, bytes, removed tool); wrong owner and unknown tool still throw `NOT_FOUND`. `photoUrl` (`ctx.storage.getUrl`) is added to `tools.list`, `tools.get` and `tools.listMine` only (signed-in queries). CSP `img-src` gains `https://*.convex.cloud` (plus `http://127.0.0.1:*` outside production, `blob:` for the local preview, `data:`), documented here per the CSP rule.

## ADR-041: Public projection stays `{ name, category }`
`tools.listPublic` is unchanged and a test asserts its exact keys even when a tool has a photo. Photos are visible to signed-in neighbors only. Signed-out visitors never get a storage URL.

## ADR-042: Orphaned uploads are swept by a cron over `_storage`
An upload URL can be used and never attached (closed tab, rejected file, attach to a foreign tool). `crons.ts` runs `toolPhotos.cleanupOrphans` every 30 minutes: it pages the `_storage` system table (100 per transaction, self-rescheduling with the cursor until the table is exhausted, so no run is unbounded), deletes files older than 1 hour that no tool references (`by_photoId`), then trims `uploadIntents` rows older than 2 hours. Chosen over tracking storage ids in `uploadIntents` because it also catches uploads that never reached us and needs no extra writes on the hot path. The app stores nothing else in `_storage`; if that changes, the sweep must learn to skip other owners.

## ADR-043: Plain `<img>` instead of `next/image`
`components/tools/tool-image.tsx` renders a plain `<img>` with `width`/`height`, `loading="lazy"`, `decoding="async"` inside a fixed 4:3 box (no layout shift) and falls back to the category illustration on load error. Convex serves the file from its own origin and the upload is capped at 2 MB and type-checked, so `next/image` would add a server-side resize hop, a `remotePatterns` entry that differs per environment (local `127.0.0.1:3210` vs `*.convex.cloud`) and a second place to keep the CSP in sync. Revisit if photos need responsive sizes. The lint rule `@next/next/no-img-element` is disabled on that single line with this ADR as the reason.

## ADR-044: Category illustrations as inline SVG components
`components/tools/category-illustration.tsx` draws one original illustration per category (drill, wrench and hammer, trowel and sprout, pot and whisk, tent, spray bottle and bucket, box) on the surface color with the brand gradient, one stroke width, `aria-hidden` (the card text names the tool). Gradient ids come from `useId` so repeated cards never collide. Seed data keeps illustrations (no photos, nothing downloaded). `public/dev/sample-tool-photo.svg` is a generated sample used only by `/dev/preview` (`?section=cards` renders just the cards for screenshots).


## ADR-045: Railway hosts n8n and Mailpit for the reviewer demo
Vercel cannot run n8n (long-lived process, volume) and Convex cannot host it, so n8n 2.46.6 and Mailpit v1.33.0 run as two Railway services built from pinned images (`deploy/railway/n8n/Dockerfile` extends the official n8n image; Mailpit uses the upstream image with env only). n8n has a public HTTPS domain (Convex must reach the webhook and reviewers need no tunnel) with its own owner login and `N8N_SECURE_COOKIE` left at the default. Mailpit's UI has a public domain behind basic auth; its SMTP port is reachable only over Railway private networking (`mailpit.railway.internal:1025`, both binds on `[::]` because that network is IPv6). Each service has a volume (`/home/node/.n8n`, `/data`). Chosen over a VPS or Fly for the single-CLI workflow and dashboard volumes; cost is the Railway Hobby plan. The build context is the repo root so the image can copy the generated workflows and the bootstrap script; a root `.dockerignore` allowlists only those files.

## ADR-046: N8N_ENCRYPTION_KEY is a Railway env var (deviation from the local secret file)
Local Docker delivers the key as a file (`N8N_ENCRYPTION_KEY_FILE`, ADR-025 rationale) so it stays out of the process environment. Railway offers only env vars (no file-mounted secrets), so on Railway the key is a service variable, generated by `scripts/deploy/gen-secrets.mjs` outside the repo and escrowed in the operator's password manager. Residual risk: the key is visible to Railway project members and in the container environment, and workflow Code nodes can read `$env` because `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` is required for signature verification (ADR-025). Accepted for a demo with throwaway data; a production host should use a secret manager mount. The key cannot be rotated against an existing volume.

## ADR-047: Workflows and credentials are bootstrapped at container start
The n8n image runs `deploy/railway/n8n/entrypoint.sh` before the server: it validates required env (names and lengths only in errors), runs `n8n/scripts/bootstrap.mjs` (credentials from env, workflows by fixed ids, publish; temp credentials dir removed on exit) and then `exec`s the base `/docker-entrypoint.sh` under tini as user `node`. Every deploy or restart therefore converges the instance to the repo's workflows and the current env secrets, so rotation is "change the variable and restart" and there is no manual import step on Railway. Bootstrap runs before the server so the restart hint is wrong in this mode; `LENDLOOP_BOOTSTRAP_AT_START=1` switches the final message and nothing else (local script and Docker flows are unchanged). Trade-off: credential edits made in the n8n UI are overwritten at the next start, and a failed bootstrap stops the container instead of serving a half-configured n8n.

## ADR-048: Mailpit is the reviewers' email inbox
The demo needs real notification emails without a transactional mail provider or verified domain. Workflow SMTP points at Mailpit over the private network, and reviewers read the mail in the Mailpit UI behind basic auth (`MP_UI_AUTH`, a single shared user with a generated alphanumeric password shared out of band). `MP_UI_AUTH` is used instead of `MP_UI_AUTH_FILE` because v1.33.0 supports it directly, which avoids a custom image to write a file at start. The UI auth applies to the API too, and no SMTP port is exposed publicly, so nobody can inject or read mail without the password. Messages are capped (`MP_MAX_MESSAGES=5000`). Real recipients never get mail, which is the intended property of a demo.

## ADR-049: The Clerk dev instance backs the demo
The existing Clerk development instance (`merry-stinkbug-7434`) serves the Vercel `*.vercel.app` deployment: no custom domain is needed (Clerk production instances require one) and the Convex integration and issuer are already configured. Known costs: a development banner, a 100-user cap, development rate limits, and `+clerk_test` emails with the fixed code 424242 for reviewers. `proxy.ts` CSP and Convex auth are unchanged. This does not replace the production requirement in `docs/PRODUCTION.md` (Clerk production instance on the project's own domain).

## ADR-050: Tab switching feels like an SPA (warm subscriptions, one signed-in layout, motion)
Problem: moving between dashboard tabs flashed skeletons, shifted the page and, for Admin, re-ran the whole shell. Measured on a signed-in test user (dev server): every revisit unmounted the tab's `useQuery` and flashed a skeleton (20 to 55 ms of `aria-busy`), the scrollbar appeared and disappeared (15 px viewport change), the footer jumped when a long tab (about 5100 px) was replaced by a short one (CLS up to 0.93), and `/admin` had its own layout so `UserBootstrap` re-mounted and showed the shell skeleton on every Admin switch.
Decisions:
- **Subscriptions stay warm** (`components/dashboard/warm-tab-data.tsx`, mounted in the shell). The user's own lists (`tools.listMine`, `loans.listMyRequests`, `loans.listIncoming` plus their batched automation timelines) stay subscribed for the whole session; the shared board (`tools.list`, unfiltered) and, for admins, the default admin listings query use `ConvexReactClient.prewarmQuery` with `extendSubscriptionFor` 5 minutes, re-armed on each navigation. Chosen over `convex-helpers` `ConvexQueryCacheProvider`: it is not installed, the native API in Convex 1.49 gives the same result for a fixed set of known tab queries, and it avoids a new dependency and a swapped `useQuery` in every component. Cost: a few live subscriptions per signed-in tab (small, user-scoped lists).
- **Category chips filter on the client.** `tools.list` is called once without args (server cap 200) and filtered with `useMemo`; the `?category=` URL stays the source of truth (`router.replace(..., { scroll: false })`). Switching is instant (no new query, no skeleton). Limit: a category is filtered from the newest 200 active tools, so beyond 200 listings a category can omit older items that a server-side filter would have returned; revisit with pagination before that scale.
- **One signed-in layout.** `app/dashboard` and `app/admin` moved into the route group `app/(app)` (URLs unchanged) with a single `layout.tsx` rendering `AppShell`, so the shell and nav never remount between tabs, including Admin.
- **`scrollbar-gutter: stable` on `html`** reserves the scrollbar track, so short and long tabs no longer shift horizontally. Supported by every current browser; where unsupported it degrades to the old behaviour.
- **Layout stability.** Header and filter row render without data (Suspense fallback for `useSearchParams` is the same filter row plus grid skeleton). Skeletons mirror the real layout (4:3 image, card padding, row heights; `ListSkeleton variant="listings"`), data regions have a `min-height`, and the Incoming badge sits in a fixed-width slot so tab widths never change. Route-level `loading.tsx` files render the header and data skeleton for a first visit.
- **Links use full prefetch** (`prefetch` on the tab links). The routes are dynamic (Clerk reads request headers), so with the default partial prefetch every click waited on a server round trip (about 300 ms in a production build, showing the `loading.tsx` skeleton on every revisit). A full prefetch is cached by the client router for 5 minutes; the pages are static client shells (all user data comes from Convex), so nothing user-specific is cached. `experimental.staleTimes` was not used (experimental flag).
- **Motion** (opacity and transform only, no layout shift): the active underline is one shared bar moved with transform and width (300 ms); the content area replays a 420 ms fade and 8 px rise per route through `app/(app)/template.tsx` (enter-only: the App Router has no exit hook and the View Transitions integration is experimental); a chip change keys the grid by category and staggers the cards by 35 ms (last starts at 245 ms); skeletons use a 1.2 s linear shimmer. Under `prefers-reduced-motion` everything is opacity only (150 ms), no stagger, no shimmer, no sliding. Animations use fill-mode `backwards` so they never pin a transform over hover styles, and they never delay content (the data is already in the DOM).
- The active tab is optimistic: the clicked href is used until the real pathname changes, so the underline moves on click rather than after the next page loads.
